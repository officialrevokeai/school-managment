# Supabase connection and data transfer

Target project: `jvheiesrkluhxebdhunh`. On 30 October 2026, connected MCP access applied all 15 checksummed app migrations to private schema `school_app` (75 tables), preserving the existing 24 `public` tables. After an encrypted backup was restored and verified, the original organization/owner/records were transferred. Exact row contents were verified across all 68 copied tables. Sessions, recovery/setup tokens and transient guards were excluded; owner password hashes and master membership were preserved. No default accounts or fictional records were added.

The restricted `school_app` login passed a real session-pooler connection with full TLS/hostname verification and the provider CA. It cannot create schema objects, modify audit history or grant master membership. All private tables have RLS policies limited to the server role; browser roles have no schema access. Server tenant/role checks remain mandatory. A production API process using live PostgreSQL returned readiness/frontend 200 and anonymous private-API 401, with approximately 112 MiB peak RSS on this Windows machine. Botkeep load/device acceptance remains unverified.

The ignored private Botkeep environment file is ready for host installation. Computer Use stopped because Chrome's current URL could not be established reliably; no further browser actions were attempted. Never publish the configuration, runtime transfer SQL, backup keys or credentials. Do not rerun initial provisioning or transfer on the populated target. Operator commands below require separate migration-owner credentials, not the restricted runtime login.

The app keeps its existing server-side login, permissions, workers and authenticated SSE updates. Supabase hosts PostgreSQL; no browser service key, public table API or replacement demonstration data is used.

1. In Supabase **Connect**, obtain the session-pooler PostgreSQL connection string (port 5432) or the direct PostgreSQL string when the host supports IPv6. Put it privately in `.env` as `DATABASE_URL`; URL-encode special password characters. Require `sslmode=verify-full&sslrootcert=deploy/certs/supabase-root.crt`. The public provider CA, source and fingerprint are included in `deploy/certs/` and the Docker image. Never disable certificate verification.
2. Set `SUPABASE_PROJECT_REF=jvheiesrkluhxebdhunh` and `DB_SCHEMA=school_app`. Keep `school_app` out of Supabase's exposed Data API schemas. The preparation script revokes `PUBLIC`, `anon` and `authenticated` access to this private schema/tables. Existing unrelated public tables are untouched. Do not expose school login hashes, sessions or private documents through REST/Realtime publications.
3. Stop the local API/worker; take and test an encrypted backup using `BACKUP_RESTORE.md`. Run `npm run build`, then `npm run supabase:prepare` using the migration-owner connection. This runs the app's existing checksummed migrations in the private schema and verifies it with a real query.
4. With the local API still stopped, run `npm run supabase:transfer`. The source is `PGLITE_PATH`; the target must be empty apart from migration metadata. The script locks target tables, copies a consistent source transaction, verifies counts and all foreign keys, and commits atomically. It refuses to overwrite nonempty targets. Sessions, recovery/setup tokens, pending deletion challenges, transient login counters and worker heartbeats are excluded. Existing credentials remain salted hashes; users must sign in again. Tests exercise PGlite-to-PGlite transfer with JSON, private file bytes and hash preservation; real Supabase transfer is still pending.
5. Configure `APP_DB_PASSWORD` privately and run `node --env-file-if-exists=.env build/scripts/configure-app-role.js` as migration owner. It creates the restricted PostgreSQL role `school_app`, grants application DML, protects append-only audits/platform events and denies master-membership writes. Replace runtime `DATABASE_URL` with this role's verified TLS connection; keep a separate migration-owner connection for future migrations. Do not use Supabase service keys or a database-owner connection in frontend code.
6. Start the API and separate worker against the same database. Verify readiness, original owner login, Master Panel totals, create/read/update from two devices, revoked school access and exports. Check Supabase advisors and confirm no app table is exposed. Run PostgreSQL/backup/restore and all nine staging release gates before production release.

MCP tools may require reopening Codex to load a newly added server. OAuth project access and the app's PostgreSQL password are separate credentials; a project reference or publishable API key is not a PostgreSQL connection string.

The runtime-role configuration script also applies `deploy/supabase-harden.sql` for the private schema. Run it only as the migration operator. It preserves the separation between the privileged operator and the restricted app role.
