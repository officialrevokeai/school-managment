# Provider implementation research

Retrieved 30 October 2026. Primary sources only. No credentials, provider API calls, recipient contact, sandbox payment, or live delivery occurred during this research. **Neither integration is live verified.**

## Meta WhatsApp Cloud API

- The official Meta Postman collection supports `POST https://graph.facebook.com/{version}/{phone-number-id}/messages`. Template payloads use `messaging_product: "whatsapp"`, `type: "template"`, template name/language and typed components. An accepted response contains a provider message ID; it establishes acceptance, not delivery. Version must be configurable. The collection includes obsolete example versions, so copying their `v13.0` example would be inappropriate. [Official template request](https://www.postman.com/meta/whatsapp-business-platform/request/lwtlz1k/send-message-template-interactive).
- The official message reference requires a registered sender phone-number ID and a token with `whatsapp_business_messaging`. Track subsequent status by provider message ID through webhooks. Do not use a submitted browser phone number as arbitrary sender identity. [Official Messages reference](https://www.postman.com/meta/whatsapp-business-platform/folder/o48mro7/messages).
- Meta's June 16, 2026 account-model briefing describes splitting the WABA into a WhatsApp Account (**WAAC**) for phone numbers and a Messaging Account (**PMA**) for templates/billing, enabling a number to be shared across partners/integrations. Persist an explicit onboarding/account model and separate provider account, sender and messaging-account references. Do not assume that every account uses the old WABA relationship. The briefing is not enough to implement or claim support for every new onboarding/API variant. [Meta account model evolution](https://developers.meta.com/resources/videos/whatsapp-account-model-evolution/).
- Existing WABA collection documentation uses `/{WABA-ID}/subscribed_apps` to subscribe the application and `/{WABA-ID}/phone_numbers` to discover phone numbers. This is evidence for that account model only. Capture the actual account/sender identifiers at setup and require callback correlation against those stored identifiers; never provision tenants based on webhook payload IDs. [Official subscription request](https://www.postman.com/meta/whatsapp-business-platform/request/0yubu4i/subscribe-app-to-whatsapp-business-account), [phone-number discovery](https://www.postman.com/meta/whatsapp-business-platform/request/hrio0ah/get-phone-number-id).
- Sender inspection is `GET /{version}/{phone-number-id}`. Successful inspection is a configuration check, not proof of template approval, recipient delivery or production readiness. [Official sender inspection](https://www.postman.com/meta/whatsapp-business-platform/request/li0unxe/get-phone-number-by-id).
- Registration requires number ownership verification; Meta's collection describes two-step verification and a register operation. Do not unregister or migrate an existing Business App number automatically. [Official registration requirements](https://www.postman.com/meta/whatsapp-business-platform/folder/zuoeksl/registration), [register request](https://www.postman.com/meta/whatsapp-business-platform/request/mk4p87j/register-phone-number).
- Meta's webhook server reference describes a GET verification token/challenge handshake and POST authenticity validation using `x-hub-signature-256` and the app secret. Implement HMAC-SHA256 over exact raw bytes, `sha256=` prefix and constant-time comparison; store authenticated events durably before acknowledging. **The Meta Node SDK is archived: use the protocol, not that SDK dependency.** The current Graph webhook page was inaccessible (429), so revalidate against authenticated current documentation at onboarding. [Meta-maintained webhook reference](https://whatsapp.github.io/WhatsApp-Nodejs-SDK/api-reference/webhooks/start/), [current webhook documentation URL](https://developers.facebook.com/docs/graph-api/webhooks/getting-started/).
- Meta's official payload collection shows the established `entry[].changes[].value` shape, with sender identity in `metadata.phone_number_id`, outbound `statuses[].id/status/timestamp`, and inbound `messages[]`. Treat this as the supported known envelope; reject/quarantine unsupported envelopes and identity forms. Preserve normalized events, deduplicate, and prevent older events regressing delivered/read state. Do not infer newer pricing/account fields from old sample payloads. [Official payload collection](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api?entity=request-13382743-ba924e99-3d98-4954-b4e3-73a519939c33).
- Current messaging policy (page updated **23 September 2026**) requires recipient-provided contact plus opt-in, honoring opt-outs, approved templates to initiate conversations, and templates outside the 24-hour service window. Authentic inbound messages reset that window. Automated replies need a clear escalation route. Avoid sensitive financial/identity/health content. Recheck consent immediately before dispatch. [WhatsApp Business Messaging Policy](https://whatsappbusiness.com/policy/).
- Meta's Direct Send briefing describes utility text via the existing messages endpoint. It does not establish eligibility, precise request fields, availability for this account, or an override of the policy. Keep optional Direct Send disabled; implement approved templates conservatively. [Meta Direct Send briefing](https://developers.meta.com/resources/videos/whatsapp-direct-send-api/).

Charges depend on current provider tariff/category/region/account terms; no cost quoted here.

## Razorpay India payment gateway

- Create orders server-side at `POST https://api.razorpay.com/v1/orders` with HTTP Basic credentials. Use authoritative integer minor-unit amount, `INR`, a unique internal receipt reference and supported notes. Browser amount is never trusted. Persist returned order ID and expected amount/currency before checkout. [Official Create Order API](https://razorpay.com/docs/api/orders/create/).
- Standard Checkout requires a server-created order linked to checkout. Payment authorization or a client callback is not settlement; captured payment moves its order to paid. Orders remain paid even after refunds, so refunds need separate accounting records. [Official Standard Checkout integration](https://razorpay.com/docs/payments/payment-gateway/web-integration/standard/integration-steps/).
- Authenticate webhooks with `X-Razorpay-Signature`: HMAC-SHA256 using the configured webhook secret and exact raw body. The webhook secret is distinct from the API key secret. Deduplicate by `x-razorpay-event-id`; events may arrive repeatedly and out of order. Retain old webhook secrets during rotation while old events can retry. [Official webhook validation](https://razorpay.com/docs/webhooks/validate-test/).
- Reconcile an event or uncertain client return through `GET /v1/payments/{id}` using server credentials. Verify order, payment ID, currency, amount, capture status and configured merchant/account identity; unknown orders must not create a tenant relationship. [Official Fetch Payment API](https://razorpay.com/docs/api/payments/fetch-with-id/).
- Apply settlement and allocation in a single locked database transaction with unique provider payment and receipt constraints. A duplicate `payment.captured`/`order.paid` observation must have one effect. Noncaptured/failed/cancelled/pending evidence creates no confirmed receipt. Preserve rejected/mismatched evidence for reconciliation.

Exact external blockers: merchant eligibility/activation, test key ID/secret, separate test webhook secret and merchant account reference, public staging HTTPS webhook, and a provider sandbox payment. Production keys and a real charge require explicit owner authorization. Razorpay currently documents localhost and many common interceptor/tunnel domains as unsuitable for callbacks; use a permitted public staging endpoint. [Official staging/test callback guidance](https://razorpay.com/docs/webhooks/validate-test/).

## Implementation and evidence boundaries

Unit tests may inject provider transports and signed fixture bytes, but must be labelled **mock/fixture tests**. They cannot establish API-version acceptance, template approval, sender onboarding, actual merchant activation, real message receipt, or authentic callbacks. Provider acceptance, sent, delivered and read are distinct observations. Ambiguous timeouts after submission require reconciliation/manual review rather than automatic blind resending. Store no tokens/secrets in frontend bundles, JSON exports, audit payloads or logs.

### Razorpay refunds

The current event reference lists `refund.created`, `refund.processed`, `refund.failed` and `refund.speed_changed`. Signed payloads place refund details under `payload.refund.entity`: `id`, `entity`, integer `amount`, `currency`, `payment_id`, `status`, `created_at`, optional `receipt`, `notes`, `acquirer_data`, `speed_processed`, `speed_requested`, `batch_id`. The envelope also includes `account_id` and a payment entity. Auto-refund events are emitted for uncaptured payments; `payload.payment.entity.captured: false` distinguishes that case. Do not reverse an allocation that never occurred. Event names alone should not supersede reconciliation: the official `refund.created` sample itself already has `status: "processed"`. [Official refund event reference and payloads](https://razorpay.com/docs/webhooks/refunds/).

Refund states are `pending`, `processed` and `failed`; `processed` is documented as final. Keep the provider refund ID unique, validate its linked captured payment and currency, and cap cumulative processed refunds at captured amount. Persist refund evidence separately from the original payment and receipt. Failed/pending refunds must not be shown as money returned. Duplicate or older events must not reverse the same allocation twice or regress a processed refund. [Official refund entity](https://razorpay.com/docs/api/refunds/entity/).

Use authenticated reads for reconciliation:

- `GET https://api.razorpay.com/v1/refunds/{refund_id}` returns the refund entity, including `payment_id`, `amount`, `currency`, `status` and acquirer references. [Fetch Refund With ID](https://razorpay.com/docs/api/refunds/fetch-with-id/).
- `GET /v1/payments/{payment_id}/refunds/{refund_id}` scopes a specific refund to its payment. Check returned `payment_id` rather than trusting client or webhook linkage. [Fetch a Specific Refund for a Payment](https://razorpay.com/docs/api/refunds/fetch-specific-refund-payment/).
- `GET /v1/payments/{payment_id}/refunds` returns a collection with `items` and `count`. Default is the last ten refunds. Paginate with integer `count` (1–100) and nonnegative `skip`; `from`/`to` filter Unix creation timestamps. Do not assume the initial page accounts for all refunds. [Fetch Multiple Refunds for a Payment](https://razorpay.com/docs/api/refunds/fetch-multiple-refund-payment/).

These reads do not authorize initiating a real refund. If initiation is added later, use its specific contract and explicit owner authorization; do not assume order creation has a generic provider idempotency header. The refund ledger policy must state whether a returned collection reopens a fee balance or corresponds to an approved cancellation/credit adjustment, and retain both records.

### Meta freeform replies

The official send-text request uses the same `POST /{version}/{phone-number-id}/messages` endpoint. The Meta-maintained example confirms `messaging_product: "whatsapp"`, `recipient_type: "individual"`, `to`, `type: "text"`, and `text: { body }`; the archived Meta text-object reference places optional `preview_url` inside the text object. Use `text: { body, preview_url: false }`. The provider response message ID still proves only acceptance. [Official send-text endpoint](https://www.postman.com/meta/whatsapp-business-platform/request/8gvd47s/send-text-message), [Meta sample source](https://github.com/fbsamples/whatsapp-api-examples/blob/main/send-messages-flight-app-python/message_helper.py), [Meta text-object reference](https://whatsapp.github.io/WhatsApp-Nodejs-SDK/api-reference/messages/text/).

Freeform availability must be calculated from the latest authentic inbound timestamp for the same stored sender and recipient identity, then rechecked at worker dispatch. The current policy permits freeform replies during that 24-hour service window; user-entered dates, an imported contact, a prior outbound send or an in-app message cannot open it. Outside it, require an approved template. Keep opt-out/scope checks and human escalation in force. The newer opaque identity mapping remains an account-specific contract blocker; retain unknown inbound identities without granting child-record access.

### Meta approved-template inspection and pagination

The official template-by-ID request is `GET https://graph.facebook.com/{version}/{template_id}`. The collection page exposes the endpoint but no usable current response schema. Fetch live provider status before using a saved template; a local save must never assert approval. Inspect name, language, category, status and supported components against the confirmed sender's messaging account. Reject missing/unrecognized fields or unsupported component/parameter formats. [Official Get template by ID](https://www.postman.com/meta/whatsapp-business-platform/request/llkzy9g/get-template-by-id-default-fields).

The official legacy collection lists templates at `GET /{version}/{waba-id}/message_templates`. Meta's collection describes paginated collection results with `paging.next`/`previous`. Follow all pages needed for a sync; never treat one page as complete or infer deleted/rejected templates from a partial sync. Validate any returned pagination URL against `https://graph.facebook.com` and the configured account/version; preferably reuse bounded cursors on the fixed endpoint, with loop/page limits. The host/path restriction is this application's security design, not a provider guarantee. [Official list-template endpoint](https://www.postman.com/meta/whatsapp-business-platform/request/qtgr0i7/get-all-templates-default-fields), [Meta collection pagination notes](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api?entity=folder-fce1b64c-b7e2-41d6-b1eb-196c74e5c1ac).

The list page is marked **MOVED** and uses the old WABA account name. The June 2026 WAAC/PMA briefing therefore remains relevant: determine the actual template-owning messaging-account reference through supported onboarding rather than guessing that a WAAC ID is a WABA ID. The new template-management and Graph results docs again returned 429, so exact newer account identifiers, default fields, approval pagination filters and named-parameter variants require authenticated contract verification. No Graph version is claimed tested by these documentation reads.
